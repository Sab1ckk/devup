# DevUp — React + FastAPI + PostgreSQL

Все команды ниже выполняются из `devup-app`. Исходный UPUP не изменяется; `template/` — его эталонная копия. Фронтенд написан на JavaScript/JSX.

## Настройка

Скопируй `.env.example` в `.env`, укажи свою `DATABASE_URL` и сгенерируй `SECRET_KEY` (например, `python -c "import secrets; print(secrets.token_urlsafe(48))"`). Настоящие секреты не записывай в `.env.example`. `.env` исключён из Git. Приложение также читает `backend/.env`; переменные окружения имеют приоритет.

Если PostgreSQL уже установлен, используй его. Для нового окружения можно запустить `docker compose up -d`; перед этим добавь `POSTGRES_PASSWORD` в `.env`. Compose содержит PostgreSQL 16 и Mailpit. На компьютере владельца установлен PostgreSQL 18, схема совместима с обоими.

```powershell
cd backend
./.venv/Scripts/python.exe -m pip install -r requirements.txt
./.venv/Scripts/python.exe -m alembic upgrade head
./.venv/Scripts/python.exe -m uvicorn main:app --reload
```

В другом терминале:

```powershell
cd frontend
npm install
npm run dev
```

Открывай адрес Vite. `/api` проксируется на `127.0.0.1:8000`. Cookie работают в одном origin. Для запуска сборки: `npm run build` в `frontend`, затем запусти FastAPI без `--reload` и открывай его адрес. FastAPI раздаёт assets и SPA-маршруты; `/api` не попадает в SPA.

## Почта

Для чтения кодов локально запусти Mailpit (`docker compose up -d mailpit`), открой http://localhost:8025 и укажи:

```dotenv
MAIL_BACKEND=smtp
SMTP_HOST=localhost
SMTP_PORT=1025
SMTP_STARTTLS=false
SMTP_USER=
SMTP_PASSWORD=
MAIL_FROM=devup@localhost
```

Для Gmail: включи двухэтапную проверку Google, создай пароль приложения и запиши его только в `.env`:

```dotenv
MAIL_BACKEND=smtp
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_STARTTLS=true
SMTP_USER=your-address@gmail.com
SMTP_PASSWORD=your-app-password
MAIL_FROM=your-address@gmail.com
```

`console` не выводит коды и токены в лог и не доставляет письма; интерфейс честно сообщает об отсутствии доставки. Для реального входа используй SMTP/Mailpit. `MailSender` изолирует транспорт; доставка фоновая, статус хранится без тела письма и секретов. `/api/mail/{uuid}` возвращает только статус доставки по непредсказуемой квитанции.

## Работа с заявками

Заявка гостя получает номер `DEVUP-1001`, секретный код и httpOnly cookie браузера. Код виден только в ответе создания и в письме, если указана почта. PDF сохраняется диалогом печати браузера. Вложения остаются макетом. Черновик сохраняется на 30 дней в `devup-mix-draft` и удаляется после отправки.

Регистрация и каждый вход требуют кода из письма. В кабинете доступны детали, история и привязка свободных заявок по браузеру, подтверждённой почте или коду. Telegram/ВК используются только как контакты. Чат не реализован: созданы только таблицы и правила доступа в `backend/app/models.py`.

CLI из `backend`:

```powershell
./.venv/Scripts/python.exe manage.py set-status 1001 in_progress --comment "Начали работу"
./.venv/Scripts/python.exe manage.py cleanup
./.venv/Scripts/python.exe manage.py create-manager your_login manager@example.com
```

Пароль менеджера вводится скрыто, не передаётся аргументом. Очистка также выполняется при старте и раз в час. Старые таблицы каталога и заказов сохранены миграцией `0002`; новые заявки записываются в `requests`, `request_*`. Клиентская роль называется `client`, старые `customer`/`admin` сохранены для совместимости. Данные из прежней `orders` автоматически не переносятся.

## Проверки

Создай отдельную БД `devup_test`, доступную той же PostgreSQL-учётной записи. Тесты намеренно очищают **только её**, рабочую базу не используют. В `.env` должна быть настроена рабочая строка; тесты подменяют имя БД. Для другого тестового подключения задай `TEST_DATABASE_URL`, имя БД обязано быть `devup_test`.

```powershell
cd backend
# Для первоначального применения миграций на тестовой базе задай DATABASE_URL в текущем терминале
# postgresql+psycopg://USER:PASSWORD@localhost:5432/devup_test
./.venv/Scripts/python.exe -m alembic upgrade head
./.venv/Scripts/python.exe -m pytest -q
cd ../frontend
npm run lint
npm run test
npm run build
npx playwright install chromium
npm run test:e2e
```

Не запускай pytest и browser-тесты одновременно: они очищают одну `devup_test`. Browser-тесты запускают отдельный тестовый сервер на 8011 и подменяют почтовый транспорт перехватчиком в памяти; специальные маршруты существуют только в `backend/tests/e2e_server.py`. Они отсутствуют в рабочем приложении. На Windows можно использовать установленный Edge: `$env:PLAYWRIGHT_CHANNEL='msedge'`. Скриншоты семи страниц на 360/768/1280 и двух палитрах находятся в `frontend/test-results/layout`. Для неизменённых страниц также выполняется пиксельное сравнение с эталоном; новые формы проверяются функционально и на отсутствие переполнения.

## Переезд

Укажи `BASE_URL`, `COOKIE_SECURE=true` при HTTPS, PostgreSQL и SMTP в переменных окружения. Сохраняй один origin. `SECRET_KEY` должен быть стабильным и секретным: замена делает старые коды недействительными. Применяй миграции перед запуском, не создавай таблицы через `create_all` при старте. SMTP, БД и секреты в сборку frontend не включаются. Лимиты и сроки вынесены в `backend/app/config.py` и могут задаваться переменными окружения. Доверенные proxy/IP нужно настраивать на сервере, произвольный `X-Forwarded-For` приложение не принимает.

Админ-панель: см. [ADMIN.md](ADMIN.md) — создание менеджера, отдельный вход, услуги, портфолио, медиа и настройки хранения.

## Чат с менеджером

Клиентские диалоги доступны на /chat после входа. Прямой диалог адресуется через ?thread=direct, диалог по заявке — через ?thread=devup-1001. Раздел менеджера — /admin/chats. Из карточек клиента и заявки можно открыть диалог, а свободная заявка получает чат после привязки к клиенту.

Переиспользованы модели ChatThread и ChatMessage из app/models.py, клиентская проверка current из app/api.py, require_admin, rate_limit, MailSender, фоновая доставка и email_log. Интерфейс использует AuthContext, AuthDialog, Dialog, lib/api и шаблонные классы чата. Клиентские и менеджерские сессии разделены.

По умолчанию сообщения содержат до 2000 символов, лимит клиента составляет 10 в минуту и 200 в сутки, менеджера — 30 в минуту. История загружается по 50 сообщений. Диалоги создаются при первой отправке или при открытии менеджером. Прочитанность у менеджеров общая. Приветствие отображается как пустое состояние. Письма без текста сообщения используют существующий SMTP, окно в 30 минут на диалог и направление и паузу после чтения в 120 секунд. Настройки CHAT_* перечислены в .env.example.

Опрос использует курсор по id каждые 5 секунд на видимой вкладке и 30 секунд на скрытой. Счётчики обновляются каждые 30 секунд у клиента и 15 секунд в админке. В API bigint-курсор передаётся строкой, чтобы избежать потери точности в JavaScript. Позже транспорт можно заменить на SSE или WebSocket, сохранив запрос истории после курсора.

Миграция 0008 меняет прежнюю пустую схему и останавливается, если в таблицах уже есть строки. После начала переписки для отката сначала нужно экспортировать и перенести данные в совместимую схему. Старые роли customer продолжают работать как клиентские роли в соответствии с существующей авторизацией.
